In the subscription implementation of this provider, Stripe owns the billing clock, the renewals, and the retry schedule. Use `@antelopejs/interface-subscriptions` in the consumer module. When Stripe takes the payments, Stripe-native subscriptions are the recommended choice.

## Create and receive events

Use a customer and a payment method saved through an on-session payment. The following function creates a monthly subscription on the selected account. Persist the idempotency key and reuse it for retries, then store the returned ID.

```typescript [subscriptions.ts] docs-check
import { CreateSubscription } from "@antelopejs/interface-subscriptions";

export async function subscribeMonthly(
  customer: string,
  paymentMethod: string,
  reference: string,
  idempotencyKey: string,
  provider?: string,
) {
  return CreateSubscription(
    {
      customer,
      paymentMethod,
      reference,
      amount: { value: 2500, currency: "EUR" },
      interval: "month",
    },
    idempotencyKey,
    provider,
  );
}
```

The provider creates the subscription with `payment_behavior: "error_if_incomplete"`. Without a trial or a future billing anchor, creation charges the first period. A declined first charge creates no subscription and throws `SubscriptionPaymentError`. Stripe voids that attempt, so the payment on the error reports `canceled`, and `providerCode` holds the decline code.

Register `SubscriptionEvents` handlers in the consumer module, and route the four subscription event types through [portable `VerifyWebhook`](./3.webhooks.md). `VerifyWebhook` awaits every registered handler. Deduplicate effects by event ID, and let processing failures propagate so that Stripe retries. A subscription-only delivery returns no payment event.

## Ownership and product

In each account, the provider creates the product with the fixed ID `antelopejs_subscriptions`, or reuses it if it exists, and creates recurring prices under it. Keep that product available. Do not archive it.

The provider owns a subscription when its metadata has the reserved key `antelope_reference`, which the provider writes when it creates the subscription. A subscription created elsewhere without that key, through Checkout, the dashboard, or `GetClient()`, is left out of reads, lists, mutations, and events. Its payments get no `antelopeSubscription` marker. Keep the ownership metadata on owned subscriptions, and do not add it to other subscriptions to get around this rule.

`GetPayment` and payment webhooks mark the charges of owned subscriptions with `metadata.antelopeSubscription`. A PaymentIntent does not carry its invoice, so the provider makes one more read, of the invoice payments that link the PaymentIntent to its invoice.

## Status and retry ownership

| Stripe status                                | Interface status |
| -------------------------------------------- | ---------------- |
| `trialing`, `active`, `past_due`, `canceled` | Same name.       |
| `unpaid`, `paused`, `incomplete`             | `past_due`       |
| `incomplete_expired`                         | `canceled`       |

`vendorData.status` holds the raw Stripe status, and `vendorData.collectionMethod` holds the collection method. The Stripe dashboard settings decide what happens after `past_due`. Configure Stripe to cancel the subscription when the retries run out. Stripe does not charge an `unpaid` subscription again, so a subscription left `unpaid` stays `past_due` in the interface with no end.

`UpdateSubscriptionPaymentMethod` changes the method for the next scheduled attempt. It does not charge right away. The provider uses epoch milliseconds, but Stripe stores times to the second, so trial and billing-anchor inputs lose their milliseconds.

## Cancellation and end semantics

`CancelSubscription(id, key, "period_end", provider)` sets `cancelAtPeriodEnd` and leaves the subscription running until the end of its paid period. `"now"` ends it at once. An ended subscription takes `endedAt` from the Stripe field `ended_at`, then from `canceled_at`, then from its creation time. It reports `endReason: "payment_failed"` only when the Stripe cancellation reason is `payment_failed`. Every other ended subscription reports `"requested"`.

Immediate cancellation is a DELETE request, so Stripe does not keep an idempotency result for it. The provider writes `antelopejs-idempotency-key:<key>` into the cancellation comment. On a retry with the same key, it finds that comment and returns the canceled subscription. Keep the comment if you rely on this recovery. Creation, period-end cancellation, and payment-method updates use Stripe POST idempotency, which Stripe keeps for at least 24 hours. After that window, reconcile uncertain outcomes as [retry safety](./2.payments.md#idempotency-and-uncertain-outcomes) describes. No replay guarantee lasts longer.

## Choose the generic scheduler explicitly

Use `@antelopejs/payment-subscriptions` only when you want the generic scheduler, which charges through the payment interface, instead of the Stripe billing clock. Add that module to the project. On the module entry of this provider, next to `source` and `config`, set `disabledExports: ["@antelopejs/interface-subscriptions"]`. Keep the payment export of the provider enabled, so that the generic scheduler can charge through it.

The following configuration selects the published modules for this setup. The generic scheduler needs a database interface, and this configuration does not provide one. Merge these entries into a project that already has it. Run `ajs project modules install`, and supply the two environment overrides before startup.

```typescript [antelope.config.ts] docs-check
import { defineConfig } from "@antelopejs/interface-core/config";

export default defineConfig({
  name: "generic-billing-project",
  modules: {
    stripe: {
      source: {
        type: "package",
        package: "@antelopejs/stripe",
        version: "^1.1.0",
      },
      disabledExports: ["@antelopejs/interface-subscriptions"],
      config: {
        apiKey: "REPLACE_VIA_ENV",
        webhookSecret: "REPLACE_VIA_ENV",
      },
    },
    subscriptions: {
      source: {
        type: "package",
        package: "@antelopejs/payment-subscriptions",
        version: "^0.0.2",
      },
    },
  },
  envOverrides: {
    STRIPE_SECRET_KEY: "modules.stripe.config.apiKey",
    STRIPE_WEBHOOK_SECRET: "modules.stripe.config.webhookSecret",
  },
});
```

The [generic scheduler documentation](https://github.com/AntelopeJS/payment-subscriptions/tree/main/docs) lists its storage and lifecycle requirements. The switch changes which scheduler bills new subscriptions. It does not move the Stripe-native subscriptions that exist. Keep one scheduler responsible for each subscription.
