The provider has two separate webhook paths. Choose the path that matches the consumer API. The built-in route does not dispatch portable payment or subscription events.

```text
Stripe -> built-in POST /stripe -> interface-stripe watchers -> optional Redis fan-out
Stripe -> your raw-body route -> VerifyWebhook -> SubscriptionEvents handlers
                                             -> returned PaymentEvent or undefined
```

## Route ownership

When a module implements the optional API interface, the provider mounts the built-in route at `config.endpoint` (default `POST /stripe`). The route verifies each delivery with the secret of the default account. It sends PaymentIntent changes to the Stripe-specific watchers and charges chargeable sources. A signature that fails verification gets `403`. The route does not call `VerifyWebhook`.

For portable payments and Stripe-native subscriptions, mount your own route and call `VerifyWebhook` from `@antelopejs/interface-payment`. Pass the account selector that belongs to that route. If you run both integrations, give each its own path and endpoint secret. Neither path forwards deliveries to the other.

## Preserve the signed bytes

Read the body as an unmodified `Buffer` or `Uint8Array` before any JSON middleware runs. Pass the original headers, `stripe-signature` included. Parsing the JSON and serializing it again changes the signed bytes. The provider looks up the header name without regard to case, and takes the first value when the signature header is an array. A missing or invalid signature rejects with `WebhookVerificationError`.

The following adapter takes a raw body that your route has already read. It does not mount a server. Call it from the raw-body route of your HTTP framework. Pass a durable payment-event processor that deduplicates by event ID, and that commits the business effects in the same transaction as the deduplication record.

```typescript [stripe-webhook.ts] docs-check
import {
  VerifyWebhook,
  WebhookVerificationError,
  type PaymentEvent,
  type WebhookRequest,
} from "@antelopejs/interface-payment";

type ProcessPaymentEvent = (event: PaymentEvent) => Promise<void>;

interface WebhookResponse {
  status: number;
}

export async function stripeWebhook(
  request: WebhookRequest,
  processPaymentEvent: ProcessPaymentEvent,
  provider?: string,
): Promise<WebhookResponse> {
  let event: PaymentEvent | undefined;
  try {
    event = await VerifyWebhook(request, provider);
  } catch (error) {
    if (error instanceof WebhookVerificationError) return { status: 403 };
    return { status: 500 };
  }

  try {
    if (event) await processPaymentEvent(event);
    return { status: 200 };
  } catch {
    return { status: 500 };
  }
}
```

Respond `200` when `VerifyWebhook` resolves with `undefined` for a verified event that has no payment outcome. Subscription-only deliveries that the handlers processed resolve the same way. When a read of extra Stripe data or your business processing fails, respond with an error so that Stripe retries. `VerifyWebhook` awaits the subscription handlers before it resolves, and the delivery fails if a handler throws. Give each handler its own durable idempotency record, because the other handlers may have succeeded already.

## Event subscriptions

On the portable endpoint, enable the Stripe event types of the features that you use:

| Stripe event                                        | Portable outcome                                                                                                      |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `payment_intent.processing`                         | `payment.pending`                                                                                                     |
| `payment_intent.amount_capturable_updated`          | `payment.authorized`                                                                                                  |
| `payment_intent.succeeded`                          | `payment.succeeded`                                                                                                   |
| `payment_intent.payment_failed`                     | `payment.failed`                                                                                                      |
| `payment_intent.canceled`                           | `payment.canceled`                                                                                                    |
| `refund.created`, `refund.updated`, `refund.failed` | `refund.succeeded` or `refund.failed`, according to the refund's terminal status. Pending refunds return `undefined`. |
| `charge.dispute.created`                            | `dispute.opened`                                                                                                      |
| `customer.subscription.created`                     | `SubscriptionEvents`: `subscription.created`                                                                          |
| `invoice.paid`                                      | `SubscriptionEvents`: `subscription.payment_succeeded` (zero-paid invoices are ignored).                              |
| `invoice.payment_failed`                            | `SubscriptionEvents`: `subscription.payment_failed`                                                                   |
| `customer.subscription.deleted`                     | `SubscriptionEvents`: `subscription.canceled`                                                                         |

`charge.refunded` does not replace the three refund events. A portable `requires_action` status comes from the result of a payment call, never from a normalized webhook event. Every other verified event type returns `undefined`.

Stripe repeats deliveries and sends them out of order. Deduplicate payment and subscription effects by event ID. When a transition is ambiguous, read the current state instead of trusting the delivery order. Invoice subscription events read the subscription again at verification time. A late redelivery can therefore show a later subscription state than the original event did.
