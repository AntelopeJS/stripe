# Receive Stripe webhooks

The provider has two separate webhook paths. Choose the path that matches the consumer API; enabling the legacy route does not dispatch portable payment or subscription events.

```text
Stripe -> built-in POST /stripe -> interface-stripe watchers -> optional Redis fan-out
Stripe -> your raw-body route -> VerifyWebhook -> SubscriptionEvents handlers
                                             -> returned PaymentEvent or undefined
```

## Route ownership

The optional API interface mounts the built-in path from `config.endpoint` (default `POST /stripe`). It verifies with the default account secret, emits legacy PaymentIntent changes and handles legacy chargeable sources. Signature failures produce `403`. It does not call `VerifyWebhook`.

For portable payments and Stripe-native subscriptions, mount your own route and call `VerifyWebhook` from `@antelopejs/interface-payment`. Pass the account selector associated with that route. Use distinct endpoint secrets and paths when you operate both integrations; neither path forwards to the other.

## Preserve the signed bytes

Read the body as an unmodified `Buffer` or `Uint8Array` before any JSON middleware. Pass the original headers including `stripe-signature`; parsing and reserializing JSON changes the signed bytes. Header-name lookup is case-insensitive and uses the first value of an array-valued signature header. Missing or invalid signatures reject with `WebhookVerificationError`.

The following complete adapter accepts an already collected raw body. Wire it into your HTTP framework's raw-body route; it does not mount a server. Supply a durable payment-event processor that deduplicates by event ID and commits business effects atomically with that deduplication record.

```typescript [stripe-webhook.ts] docs-check
import {
  VerifyWebhook,
  WebhookVerificationError,
  type PaymentEvent,
  type WebhookRequest,
} from "@antelopejs/interface-payment";

type ProcessPaymentEvent = (event: PaymentEvent) => Promise<void>;

interface WebhookResponse {
  status: number;
}

export async function stripeWebhook(
  request: WebhookRequest,
  processPaymentEvent: ProcessPaymentEvent,
  provider?: string,
): Promise<WebhookResponse> {
  let event: PaymentEvent | undefined;
  try {
    event = await VerifyWebhook(request, provider);
  } catch (error) {
    if (error instanceof WebhookVerificationError) return { status: 403 };
    return { status: 500 };
  }

  try {
    if (event) await processPaymentEvent(event);
    return { status: 200 };
  } catch {
    return { status: 500 };
  }
}
```

Respond `200` for a genuine unsupported event (`undefined`), including successfully processed subscription-only deliveries. Respond with an error when enrichment or business processing fails so Stripe retries. `VerifyWebhook` awaits subscription handlers before resolving; if a handler throws, the delivery fails. Each handler needs its own durable idempotency boundary because other handlers may already have succeeded.

## Event subscriptions

Enable these exact Stripe event types on the portable endpoint for the features you use:

| Stripe event                                        | Portable outcome                                                                                                      |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `payment_intent.processing`                         | `payment.pending`                                                                                                     |
| `payment_intent.amount_capturable_updated`          | `payment.authorized`                                                                                                  |
| `payment_intent.succeeded`                          | `payment.succeeded`                                                                                                   |
| `payment_intent.payment_failed`                     | `payment.failed`                                                                                                      |
| `payment_intent.canceled`                           | `payment.canceled`                                                                                                    |
| `refund.created`, `refund.updated`, `refund.failed` | `refund.succeeded` or `refund.failed`, according to the refund's terminal status. Pending refunds return `undefined`. |
| `charge.dispute.created`                            | `dispute.opened`                                                                                                      |
| `customer.subscription.created`                     | `SubscriptionEvents`: `subscription.created`                                                                          |
| `invoice.paid`                                      | `SubscriptionEvents`: `subscription.payment_succeeded` (zero-paid invoices are ignored).                              |
| `invoice.payment_failed`                            | `SubscriptionEvents`: `subscription.payment_failed`                                                                   |
| `customer.subscription.deleted`                     | `SubscriptionEvents`: `subscription.canceled`                                                                         |

`charge.refunded` is not a substitute for the three refund events. Portable `requires_action` is learned synchronously from a payment result, not from a normalized webhook event. Other genuine event types return `undefined`.

Deliveries repeat and arrive out of order. Deduplicate payment and subscription effects by event ID, and reconcile ambiguous transitions with a read rather than assuming delivery order equals state order. Invoice subscription events read the subscription back at verification time: a late redelivery can show a later subscription state than the original event.
